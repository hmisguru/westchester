# westchester-kpis

Public repo: embeddable HUD System Performance Measure KPIs for the Westchester County CoC (NY-604), built with Observable Framework (`src/`, config in `observablehq.config.js`) and deployed to GitHub Pages (https://hmisguru.github.io/westchester-kpis/) by `.github/workflows/deploy.yml`. Companion to the private `hmisguru/westchester` repo (DAC `wcspm.yml` dashboard), which is where the data and query logic come from. Modeled directly on `hmisguru/baltimore-kpis`, with the project-funding-filter concept removed entirely (see "No funding filter" below).

**This repo is public.** Never commit credentials, row-level data, internal service IDs/URLs, or anything from `hmisguru/westchester`'s CLAUDE.md beyond what's needed here. Only CoC-wide aggregates are published. No small-count suppression is applied, per Baltimore's own precedent: every KPI is a system-wide total or rate.

## Data flow

- `sql/*.sql` are **generated copies** of every `type: table` widget in `wcspm.yml` (System Performance Dashboard, `main` branch of `hmisguru/westchester`) — 9 total, Measures 1, 2, 3.2, 4, 5.1, 5.2, 7a.1, 7b.1, 7b.2 — rendered with no Project filter and with `{{ filters.report_start }}` turned into the BigQuery parameter `@report_start`. Regenerate with `scripts/extract_sql.py <path to wcspm.yml>` whenever the dashboard's measure logic changes; never hand-edit, or the published numbers will drift from the dashboard. 6 of the 9 feed the public KPI tiles (below); all 9 feed the full dashboard page (`/spm/`, see "Full System Performance Dashboard" below).
- `src/data/spm.json.py` is the KPI-tile data loader, reading from BigQuery project `bruin-508014` (`wchmiscsv`/`clienttrack`-equivalent datasets live there, not `baldash-508920`). It reads `MAX(ExportEndDate)` from `wchmiscsv.Export`, reports the most recent **complete** federal fiscal year ending on or before it (FY = Oct 1 – Sep 30), and compares against the prior FY. Measures 1 and 2 are single-period queries, so they run once per FY; 3.2, 5.1, 7a.1 and 7b.1 already return Current/Previous FY columns. It picks one row per measure by exact label and `sys.exit`s if a label is missing (so a changed dashboard query fails the build instead of publishing nulls) — **except** Measure 7a.1's universe row, which `pick()` defaults to `{current_fy: 0, previous_fy: 0}` instead of failing, kept as a defensive fallback rather than removed — see "Street Outreach" below for why.
- `src/data/spm-dashboard.json.py` is a second, separate loader for the full dashboard page (`/spm/`) — same fiscal-year logic as `spm.json.py` (duplicated rather than shared, since the two loaders return differently-shaped documents: a handful of picked KPI values vs. every row of all 9 widgets), but runs all 9 widgets in full and keeps every result row, with each widget's own `columns` config (label, number format) copied from `wcspm.yml` so the page renders identically to the dashboard. No `pick()`/`sys.exit` validation here — an empty or reshaped result just renders as an empty table (`spm-dashboard.js`'s `empty()`), matching how DAC itself handles it.
- KPI ids are hardcoded in both the KPI loader (`"id"` fields) and `observablehq.config.js` (`kpiIds`, used for the `/embed/<id>` dynamic paths). Keep the two lists in sync.
- Auth: Application Default Credentials. In CI, the `GCP_SERVICE_ACCOUNT_JSON` repository secret is written to a temp file and pointed to by `GOOGLE_APPLICATION_CREDENTIALS`. This repo's service account needs read-only access to `wcdashboard`/`wchmiscsv` on project `bruin-508014` — a separate credential from Baltimore's `balkpis-public@baldash-508920.iam.gserviceaccount.com`, scoped to a different GCP project entirely.

## No funding filter

Unlike `baltimore-kpis`, there is no MOHS-funded/project-scope split here, per explicit user choice when this repo was commissioned. `hmisguru/westchester`'s `wchmiscsv` has no `Funder` table at all, so there's no equivalent concept to filter by. Every KPI, and `wcspm.yml`'s own Measure 4 (Income Growth) that this repo doesn't surface, is scoped to all TH/SH/PH (or ES/SH/TH, per measure) projects CoC-wide. `kpi.js`'s `scopeData`/`toggle`/`mohsFunded` machinery from the Baltimore version is removed entirely, not just unused — there is nothing to toggle.

## Street Outreach

At this repo's creation, the Westchester CoC had zero active Street Outreach (ProjectType 4) projects, confirmed directly against `wchmiscsv.Project`. Per explicit user choice at the time ("Keep both tiles exactly as Baltimore has them"), the `street-outreach-exits` and `exits-to-permanent-housing` tiles were kept unchanged from Baltimore's version rather than relabeled or dropped, even though `street-outreach-exits` necessarily read 0 for both fiscal years (a correct zero-universe result, not an error) and `exits-to-permanent-housing`'s entire contribution came from 7b.1 (ES/SH/TH/RRH/other PH exits) alone. `sql/m7_exits_to_ph.sql` still unions the 7a.1 `classified` CTE with 7b.1's, so the file stays structurally identical to Baltimore's and needs no special-casing.

**As of 2026-10-01, `wchmiscsv` has 17 Street Outreach projects** (confirmed live, after a `wchmiscsv` data refresh) — the zero-project state above no longer holds, and both tiles now report real, nonzero figures. The KPI descriptions were updated to drop the "no active Street Outreach projects" caveat accordingly. The `pick()` default in `src/data/spm.json.py` (falling back to `{current_fy: 0, previous_fy: 0}` for Measure 7a.1's universe row when the query returns no rows at all, rather than a zero-valued row) is kept as a defensive fallback rather than removed, in case Street Outreach project counts ever revert to zero — see that function's own docstring.

## Full System Performance Dashboard (`/spm/`)

A static Observable rendering of every measure widget in `wcspm.yml`, not just the 6 summarized as KPI tiles — the closest Westchester equivalent of `baltimore-kpis`'s `/bridge/`/`/coordinated-entry/` full-dashboard prototypes, built on explicit request ("just like we did for Baltimore"). Per explicit instruction, it's modeled directly on `balspm.yml` (`hmisguru/baltimore`, `staging` branch) rather than `wcspm.yml` alone, since the two had drifted: `wcspm.yml` (`hmisguru/westchester`, `main`) is missing `balspm.yml`'s "Dashboard Notes" intro widget entirely, and lists its 9 measure widgets in a different row order (Metric 3.2 first, rather than Measures 1a/1b first). `src/spm/index.md` follows `balspm.yml`'s order and includes an adapted version of its notes text (`renderNotes()` in `spm-dashboard.js`) — `wcspm.yml` itself was NOT changed to match; that's a separate, not-yet-requested fix in the `hmisguru/westchester` repo.

- **CoC-wide only, no interactive filters** — per explicit choice, this page shows only CoC-wide figures for the current vs. previous fiscal year, refreshed only when the site rebuilds. There is no Fiscal Year Start Date control (same reasoning the public KPI tiles already use in `spm.json.py`'s `run_measure()`: `report_start` is a continuous date, so there's no finite set of values to precompute) and no Project filter.
- **A per-project single-select dropdown existed briefly and was archived, not deleted** — per explicit request. It ran every one of the 9 widgets once CoC-wide and once per "active SPM project" (open, HUD-SPM-covered project type; 121 of 179 `ContinuumProject = 1` projects as of 2026-10-01) — 9 × 122 = 1,098 BigQuery queries per build, confirmed to complete in under 2 minutes in CI. The full working loader (`spm-dashboard.json.py`), renderer (`spm-dashboard.js`), and the CSS it needs (`spm-dashboard.css`) are preserved at `archive/`, with a README there on how to reactivate it. A multi-select was never built: several widgets' per-person dedup logic (returns, first-time, retention) spans the whole selected universe at once, so summing two projects' independently-precomputed rows would double-count clients active in both — each dropdown option had to be its own full, independently-correct query, not a combination of smaller pieces.
- Widget order and titles match `wcspm.yml` exactly (which already differs from `balspm.yml` in two places by explicit design, not drift: Measure 4's title and its broader TH/SH/PH-not-CoC-funded-only scope, documented under "No funding filter" above).
- `src/components/spm-dashboard.js`/`.css` render it: `renderNotes()` for the intro box, `renderDashboard()` for the 9 measure tables (plain HTML tables via each widget's own `columns` config — no conditional-format pills, since none of `wcspm.yml`'s table columns use them, unlike `baltimore-kpis`'s Bridge tables). Class prefix `spmd-`, distinct from `kpi.js`'s `wkpi-` and the rest of the site, since this isn't an embeddable module.
- Linked from the KPI homepage (`src/index.md`) and links back to it; not added to `dynamicPaths` (no embed/iframe variant requested for this page, unlike the KPI tiles).
- **Light/dark toggle, default light** — `renderThemeToggle()` in `spm-dashboard.js` sets `document.documentElement.dataset.theme`, persisted in `localStorage` (`spmd-theme`) so a return visit keeps the visitor's last choice, but every first-ever visit starts light regardless. Unlike `kpi.js`'s `data-theme` option (a prop the embedding page sets once, no UI), this is a visible button the visitor clicks, since `/spm/` is a standalone page rather than an embedded tile. The dark palette reuses `kpi.js`'s own `data-theme="dark"` colors (`#02372d` surface, `#3dc372` accent, white text) for consistency with the KPI tiles elsewhere on this site. Implementation note: rather than switching Framework's own `theme:` config (which only supports OS-preference-driven `prefers-color-scheme` dual themes, not a manual toggle), `spm-dashboard.css` overrides Framework's `--theme-foreground`/`--theme-background-*` custom properties under `html[data-theme="dark"]` — higher specificity than Framework's own `:root` declarations, same element — which flips the page background/text/link color for free via `global.css`'s existing `var()` consumption; only `.spmd-*`'s own hardcoded-hex colors need explicit dark overrides.

## Measure 2 deviation: stacked PH subsidy enrollments

`sql/m2_returns.sql` (which feeds both the `returns-to-homelessness` KPI tile and the full dashboard's Measure 2 table) deviates from the HUD programming specs by explicit choice: if a client has a still-open PH enrollment that began within 14 days of a qualifying exit (their successful placement), no later PH entry counts as a return to homelessness, however far outside the normal 14-day window it starts. HUD's spec has no provision for a client remaining in that same placement under a second, stacked PH subsidy program (multiple funding sources covering one household's housing) — taken literally, it misreads that second enrollment as a new homelessness episode. Surfaced and confirmed live via `hmisguru/westchester`'s own `wcspm.yml` (that repo's commit history has the full investigation): PersonalID 13523 moved into an open-ended PH placement the day before their qualifying shelter exit and started a second, distinct PH enrollment over a year later — correctly not counted as a return. Regenerate this file (and the other 8) with `scripts/extract_sql.py` whenever `wcspm.yml`'s Measure 2 logic changes; the deviation lives in the dashboard source, not here.

## Zero-length (same-day entry/exit) enrollments

Three fixes to `sql/m1_length_of_time.sql`, `sql/m2_returns.sql`, and `sql/m3_sheltered.sql`, all sourced from `hmisguru/westchester`'s `wcspm.yml` and re-extracted here — see that repo's commit history for the full investigation and live BigQuery confirmation of each:

- **Metric 3.2** (`m3_sheltered.sql`): its `ee_based` active-client test now also requires `ExitDate > EntryDate`, so a same-day ES-EE/TH/SH enrollment (zero documented nights) no longer counts as "active" — it was previously satisfying the period-overlap test despite representing zero nights, which violated the widget's own "Active Clients - Method 5: 1+ Nights Active" methodology.
- **Measure 1** (`m1_length_of_time.sql`): `nbn_earliest` now derives from `nbn_nights` directly instead of re-deriving its own entry/exit bounds, fixing a one-day inconsistency between the two (pure consistency cleanup — same-day enrollments already contributed zero nights to this measure either way).
- **Measure 2** (`m2_returns.sql`): a zero-length candidate enrollment no longer counts as a return to homelessness, **except in Street Outreach** (SO isn't residential — a client can legitimately be contacted as street homeless on a single day, while a same-day ES/TH/SH/PH enrollment is presumed to be a data-entry artifact rather than a genuine re-entry). Also fixed a self-match bug where the very enrollment that produced a client's qualifying "exited to PH" row could, when zero-length, match as its own return — `bucketed` now carries `EnrollmentID` so `matches` can exclude it from matching itself.

## Embedding surfaces (keep all three working)

1. **Iframes**: `src/embed/[kpi].md` (one parameterized page per KPI) and `src/embed/all.md` (grid). Chrome-free (no header/footer/sidebar), `?theme=light|dark|auto` override.
2. **Exported JS module**: `src/kpis.js` → published unhashed at `/kpis.js` via `dynamicPaths`. Exports `KPI(id, options)`, `KPIGrid(ids, options)`, `data()`. Its `FileAttachment` resolves relative to `import.meta.url`, so cross-origin imports work (GitHub Pages sends `Access-Control-Allow-Origin: *`).
3. **Raw JSON**: `/data/spm.json`, also via `dynamicPaths`.

`src/components/kpi.js` is the one tile renderer all three share: plain DOM, no dependencies, self-injected CSS scoped to `.wkpi` (not `.bkpi` — a distinct prefix, since this is a separate published module, not a copy sharing Baltimore's `--bkpi-*` custom property names), restylable via `--wkpi-*` custom properties.

**Styled to match `socialservices.westchestercountyny.gov`** (Westchester County's Department of Social Services site), per explicit request. Colors and font names were pulled from that site's own live CSS (`theme.12.css`, `custom.css`) and Adobe Fonts kits, not guessed:
- `#02372D` (deep forest green) is that site's own `.uk-button-primary`/`.uk-button-secondary` background and its `.uk-section-secondary` dark-section color (paired with white text, `--uk-inverse: light`) — used here as the top-stripe/eyebrow accent in light mode, and reused as the dark-mode `--wkpi-surface` to match that same dark-green-with-white-text convention.
- `#3DC372`/`#E44E56` are that site's own success/danger colors (not generic Bootstrap defaults — confirmed by occurrence count in the theme CSS) — used for the Improved/Worsened arrows instead of this module's prior generic green/red.
- `#2D2E33`/`#6C6D74` (body/secondary text) and `#D4D3D6` (borders) come directly from that site's own heading and nav-link rules.
- Fonts: `"sofia-pro"` (that site's body font, via Adobe Fonts kit `lmh6uec`) and `"degular"` (that site's display-heading font, via kit `iqf2dwz`, used here only for `.wkpi-value` and `.wkpi-measure`, matching how that site reserves it for large headings). Both kits are domain-locked to `westchestercountyny.gov` and won't load on any other host, so `ensureStyle()` also injects a Google Fonts `<link>` for `Work Sans`/`Sora` (close free matches) as the fallback — real fonts if this is ever embedded on that site itself, a deliberately close look everywhere else. `observablehq.config.js`'s own `head` loads the same fallback fonts for this site's own pages (`index.md`, the embed pages).
- If this branding ever needs to change, update the `CSS`/`DARK` constants in `kpi.js` and the `head`/`footer`/`theme` keys in `observablehq.config.js` together — they're meant to stay in sync.

Light by default (`theme: "dark"` or `"auto"` opt in). In `renderKpiGrid`, tiles use CSS subgrid (`grid-row: span <tile part count>` + `grid-template-rows: subgrid`) so each part (label, title, value, change, description) aligns across tiles in the same row even when titles wrap differently; browsers without subgrid fall back to normal stacking. Delta color is never the only signal: every tile shows an arrow plus an "Improved"/"Worsened"/"No change" label, based on each KPI's `better` direction.

**No visible Observable branding**, matching Baltimore's precedent: the site footer is set explicitly (unset, Framework adds "Built with Observable"), no page text names it, and `scripts/strip_generator.js` (run by `npm run build`) removes Framework's `<meta name="generator">` tag from the built pages.

**No Bridge/Coordinated-Entry-style prototype dashboard** — per explicit scoping, this repo is KPI tiles only, unlike `baltimore-kpis`'s `/bridge/` and `/coordinated-entry/` full-dashboard prototypes. Don't add one without being asked.

## Scheduling

Monthly on the first Wednesday (13:17 UTC), plus on push to `main` and manual dispatch. Cron ORs day-of-month with day-of-week, so the schedule fires every Wednesday (`17 13 * * 3`) and a `schedule-gate` job skips `build`/`deploy` unless the UTC date is the 1st-7th; pushes and manual runs always build. No daily cron (unlike `baltimore-kpis`, which added one for its Coordinated Entry prototype's "this month" freshness) — these KPIs only ever change when a new HMIS CSV export lands, which a monthly rebuild already keeps pace with. GitHub disables scheduled workflows in public repos after 60 days of no repo activity; the `keepalive` job re-enables the workflow via the API on each scheduled run to reset that clock.
