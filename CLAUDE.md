# westchester

Public repo: embeddable HUD System Performance Measure KPIs for the Westchester County CoC (NY-604), built with Observable Framework (`src/`, config in `observablehq.config.js`) and deployed to GitHub Pages (https://hmisguru.github.io/westchester/) by `.github/workflows/deploy.yml`. Companion to the private `hmisguru/westchester-dac` repo (DAC `wcspm.yml` dashboard), which is where the data and query logic come from. There is no project-funding-filter concept here (see "No funding filter" below).

**This repo is public.** Never commit credentials, row-level data, internal service IDs/URLs, or anything from `hmisguru/westchester-dac`'s CLAUDE.md beyond what's needed here. Only CoC-wide aggregates are published. No small-count suppression is applied, per explicit choice: every KPI is a system-wide total or rate.

## Data flow

- `sql/*.sql` are **generated copies** of every `type: table` widget in `wcspm.yml` (System Performance Dashboard, `main` branch of `hmisguru/westchester-dac`) — 9 total, Measures 1, 2, 3.2, 4, 5.1, 5.2, 7a.1, 7b.1, 7b.2 — rendered with no Project filter and with `{{ filters.report_start }}` turned into the BigQuery parameter `@report_start`. Regenerate with `scripts/extract_sql.py <path to wcspm.yml>` whenever the dashboard's measure logic changes; never hand-edit, or the published numbers will drift from the dashboard. 6 of the 9 feed the public KPI tiles (below); all 9 feed the full dashboard page (`/spm/`, see "Full System Performance Dashboard" below). `sql/street_outreach_active.sql` is the one exception in this directory — hand-written, not generated, since it has no `wcspm.yml` widget to copy from; see "People in Street Outreach (non-HUD metric)" below.
- `src/data/spm.json.py` is the KPI-tile data loader, reading from BigQuery project `bruin-508014` (`wchmiscsv`/`clienttrack`-equivalent datasets live there). It reads `MAX(ExportEndDate)` from `wchmiscsv.Export`, reports the most recent **complete** federal fiscal year ending on or before it (FY = Oct 1 – Sep 30), and compares against the prior FY. Measures 1 and 2 are single-period queries, so they run once per FY; 3.2, 5.1, 7a.1 and 7b.1 already return Current/Previous FY columns. It picks one row per measure by exact label and `sys.exit`s if a label is missing (so a changed dashboard query fails the build instead of publishing nulls) — **except** Measure 7a.1's universe row, which `pick()` defaults to `{current_fy: 0, previous_fy: 0}` instead of failing, kept as a defensive fallback rather than removed — see "Street Outreach" below for why.
- `src/data/spm-dashboard.json.py` is a second, separate loader for the full dashboard page (`/spm/`) — same fiscal-year logic as `spm.json.py` (duplicated rather than shared, since the two loaders return differently-shaped documents: a handful of picked KPI values vs. every row of all 9 widgets), but runs all 9 widgets in full and keeps every result row, with each widget's own `columns` config (label, number format) copied from `wcspm.yml` so the page renders identically to the dashboard. No `pick()`/`sys.exit` validation here — an empty or reshaped result just renders as an empty table (`spm-dashboard.js`'s `empty()`), matching how DAC itself handles it.
- KPI ids are hardcoded in both the KPI loader (`"id"` fields) and `observablehq.config.js` (`kpiIds`, used for the `/embed/<id>` dynamic paths). Keep the two lists in sync.
- Auth: Application Default Credentials. In CI, the `GCP_SERVICE_ACCOUNT_JSON` repository secret is written to a temp file and pointed to by `GOOGLE_APPLICATION_CREDENTIALS`. This repo's service account needs read-only access to `wcdashboard`/`wchmiscsv` on project `bruin-508014`, scoped to this GCP project alone.

## No funding filter

There is no funded-project-scope split here, per explicit user choice when this repo was commissioned. `hmisguru/westchester-dac`'s `wchmiscsv` has no `Funder` table at all, so there's no equivalent concept to filter by. Every KPI, and `wcspm.yml`'s own Measure 4 (Income Growth) that this repo doesn't surface, is scoped to all TH/SH/PH (or ES/SH/TH, per measure) projects CoC-wide. `kpi.js` has no `scopeData`/`toggle`/funded-scope machinery at all here — there is nothing to toggle.

## Street Outreach

At this repo's creation, the Westchester CoC had zero active Street Outreach (ProjectType 4) projects, confirmed directly against `wchmiscsv.Project`. Per explicit user choice at the time, the `street-outreach-exits` and `exits-to-permanent-housing` tiles were kept unchanged rather than relabeled or dropped, even though `street-outreach-exits` necessarily read 0 for both fiscal years (a correct zero-universe result, not an error) and `exits-to-permanent-housing`'s entire contribution came from 7b.1 (ES/SH/TH/RRH/other PH exits) alone. `sql/m7_exits_to_ph.sql` still unions the 7a.1 `classified` CTE with 7b.1's, so the file needs no special-casing.

**As of 2026-10-01, `wchmiscsv` has 17 Street Outreach projects** (confirmed live, after a `wchmiscsv` data refresh) — the zero-project state above no longer holds, and both tiles now report real, nonzero figures. The KPI descriptions were updated to drop the "no active Street Outreach projects" caveat accordingly. The `pick()` default in `src/data/spm.json.py` (falling back to `{current_fy: 0, previous_fy: 0}` for Measure 7a.1's universe row when the query returns no rows at all, rather than a zero-valued row) is kept as a defensive fallback rather than removed, in case Street Outreach project counts ever revert to zero — see that function's own docstring.

## People in Street Outreach (non-HUD metric)

`people-in-street-outreach` is a 7th KPI tile, invented on explicit request rather than drawn from `wcspm.yml` -- **HUD's real SPM spec has no "Measure 3.3"**; Measure 3 only defines 3.1 (PIT counts, not generated from HMIS) and 3.2 (Unduplicated Sheltered Persons). Per explicit choice, this tile drops HUD numbering entirely rather than implying an official measure that doesn't exist:

- `kpi.js`'s tile eyebrow normally renders `HUD ${kpi.measure}`; this is the one tile where the KPI object sets `eyebrow` directly (`"Local Measure 3.3"`, per explicit choice -- reads consistently alongside the numbered HUD tiles while still flagging it's not one of them; briefly labeled "Dashboard metric" before that) instead of `measure`, which `renderKpi()` now prefers when present (`kpi.eyebrow ?? \`HUD ${kpi.measure}\``) -- every other tile is unaffected, since none of them set `eyebrow`.
- Not on the `/spm/` full dashboard page -- that page is explicitly a 1:1 rendering of `wcspm.yml`'s own 9 widgets (`spm-dashboard.json.py`'s `WIDGETS` list, "same widget order" per its own docstring), and this metric has no `wcspm.yml` widget to mirror. KPI tiles only.
- `sql/street_outreach_active.sql` is hand-written (see its own header comment) rather than generated by `scripts/extract_sql.py`, since there's no source widget to extract from. It still takes the same `@report_start` BigQuery parameter as every other query (passed via `spm.json.py`'s `run_measure()`, same as the rest), just doesn't reference the unused `@all_projects`/`@project_ids` parameters that `run_measure()` always supplies -- confirmed live that BigQuery accepts declared-but-unreferenced named parameters without error.
- **Universe, modeled on Metric 3.2's comparison layout but with Metric 3.2's own zero-length-enrollment exclusion deliberately left out**: any Street Outreach (ProjectType 4, CoC-participating) enrollment active during the fiscal year (`EntryDate <= period_end AND (ExitDate IS NULL OR ExitDate > period_start)`), counted unduplicated per person. Per explicit choice: Street Outreach isn't residential, so a client can legitimately be contacted as street homeless on a single day with no multi-day enrollment span to speak of -- the same reasoning already applied to Measure 2's return-to-homelessness matching (`sql/m2_returns.sql`'s `has_duration` flag, which likewise never applies to ProjectType 4). Confirmed live (`report_start = 2025-10-01`): 336 current FY vs. 486 previous FY.
- `better: None` (neutral gray arrow, no Improved/Worsened label) — same reasoning as `street-outreach-exits`: neither direction is inherently better, since fewer people found in Street Outreach could mean less homelessness or just less outreach contact.
- Considered and rejected as the universe definition: a `CurrentLivingSituation = 116` ("place not meant for habitation") contact-based count, mirroring a stricter "currently unsheltered" convention more closely (confirmed live: 149 current FY vs. 243 previous FY under that definition). Not used, per explicit choice for the simpler enrollment-overlap definition instead, matching Measure 3.2's own approach more directly.

## Full System Performance Dashboard (`/spm/`)

A static Observable rendering of every measure widget in `wcspm.yml`, not just the 6 summarized as KPI tiles, built on explicit request. Per explicit instruction, it's modeled on a fuller dashboard-notes template rather than `wcspm.yml` alone, since the two had drifted: `wcspm.yml` (`hmisguru/westchester-dac`, `main`) is missing that template's "Dashboard Notes" intro widget entirely, and lists its 9 measure widgets in a different row order (Measure 3.2 first, rather than Measures 1a/1b first). `src/spm/index.md` follows that template's order and includes an adapted version of its notes text (`renderNotes()` in `spm-dashboard.js`) — `wcspm.yml` itself was NOT changed to match; that's a separate, not-yet-requested fix in the `hmisguru/westchester-dac` repo.

- **CoC-wide only, no interactive filters** — per explicit choice, this page shows only CoC-wide figures for the current vs. previous fiscal year, refreshed only when the site rebuilds. There is no Fiscal Year Start Date control (same reasoning the public KPI tiles already use in `spm.json.py`'s `run_measure()`: `report_start` is a continuous date, so there's no finite set of values to precompute) and no Project filter.
- **A per-project single-select dropdown existed briefly and was archived, not deleted** — per explicit request. It ran every one of the 9 widgets once CoC-wide and once per "active SPM project" (open, HUD-SPM-covered project type; 121 of 179 `ContinuumProject = 1` projects as of 2026-10-01) — 9 × 122 = 1,098 BigQuery queries per build, confirmed to complete in under 2 minutes in CI. The full working loader (`spm-dashboard.json.py`), renderer (`spm-dashboard.js`), and the CSS it needs (`spm-dashboard.css`) are preserved at `archive/`, with a README there on how to reactivate it. A multi-select was never built: several widgets' per-person dedup logic (returns, first-time, retention) spans the whole selected universe at once, so summing two projects' independently-precomputed rows would double-count clients active in both — each dropdown option had to be its own full, independently-correct query, not a combination of smaller pieces.
- Widget order and titles match `wcspm.yml` exactly (which already differs from that template in two places by explicit design, not drift: Measure 4's title and its broader TH/SH/PH-not-CoC-funded-only scope, documented under "No funding filter" above).
- `src/components/spm-dashboard.js`/`.css` render it: `renderNotes()` for the intro box, `renderDashboard()` for the 9 measure tables (plain HTML tables via each widget's own `columns` config — no conditional-format pills, since none of `wcspm.yml`'s table columns use them). Class prefix `spmd-`, distinct from `kpi.js`'s `wkpi-` and the rest of the site, since this isn't an embeddable module.
- **`renderNotes()`'s box renders below the 9 tables, not above them, collapsed behind a native `<details>/<summary>`** ("About this data", per explicit request) — the tables are the first thing in view rather than being pushed down by that long paragraph. `spm/index.md`'s own script cell wraps the `<div class="spmd-notes">` `renderNotes()` returns in a `<details class="spmd-notes-details">`; `.spmd-notes` itself (the box background/border/padding) is untouched, only its position and this wrapper changed. `.spmd-notes-details`'s summary styling lives in `spm-dashboard.css`, lightweight to match `index.md`'s own `.note-details` convention.
- Linked from the KPI homepage (`src/index.md`) and links back to it; not added to `dynamicPaths` (no embed/iframe variant requested for this page, unlike the KPI tiles).
- **Light/dark toggle, default light** — `renderThemeToggle()` in `spm-dashboard.js` sets `document.documentElement.dataset.theme`, persisted in `localStorage` (`spmd-theme`) so a return visit keeps the visitor's last choice, but every first-ever visit starts light regardless. Unlike `kpi.js`'s `data-theme` option (a prop the embedding page sets once, no UI), this is a visible button the visitor clicks, since `/spm/` is a standalone page rather than an embedded tile. The dark palette reuses `kpi.js`'s own `data-theme="dark"` colors (`#02372d` surface, `#3dc372` accent, white text) for consistency with the KPI tiles elsewhere on this site. Implementation note: rather than switching Framework's own `theme:` config (which only supports OS-preference-driven `prefers-color-scheme` dual themes, not a manual toggle), `spm-dashboard.css` overrides Framework's `--theme-foreground`/`--theme-background-*` custom properties under `html[data-theme="dark"]` — higher specificity than Framework's own `:root` declarations, same element — which flips the page background/text/link color for free via `global.css`'s existing `var()` consumption; only `.spmd-*`'s own hardcoded-hex colors need explicit dark overrides.
- **The KPI home page (`src/index.md`) reuses this same toggle**, importing `renderThemeToggle()` directly from `spm-dashboard.js` and linking `spm-dashboard.css`, rather than building a near-duplicate — a deliberate choice to share the `spmd-theme` localStorage key across both pages, since they're tightly coupled views of the same KPI dataset and already cross-link to each other in-page. `renderKpiGrid()`'s own theme is a prop set once at render time, not a `[data-theme]` cascade, so `index.md`'s script cell also pushes the toggle's current state onto the grid wrapper and each `.wkpi` tile by hand (on load and again on every toggle click) to keep the tiles in sync; `kpi.js` itself is untouched, since it's published externally via `dynamicPaths`. The home page's "About this data" note is also collapsed behind a native `<details>/<summary>` (`.note-details` in `index.md`'s own `<style>` block), lightweight by design since the note had no CSS before that either.
- **Share controls (copy link, email) — built, currently unused, per explicit request.** `src/components/share.js`/`.css` hold a working, page-agnostic `renderShareControls()` (a "Copy link" button via the Clipboard API with a graceful text-only fallback if it's unavailable, plus an "Email" `mailto:` link prefilled with a subject/body each page would pass in and the current page URL), styled to match `.spmd-theme-toggle`'s pill shape/palette. Neither `index.md` nor `spm/index.md` imports or links it right now — shipped once, then explicitly hidden shortly after without being deleted, so it's a quick re-add (import + link tag + appending its result into `.page-controls` alongside the toggle, same as before) rather than a rebuild if it's wanted again later. `.page-controls`'s own `margin-top: 8px` (see the toggle bullet above) stays regardless of whether share controls are present — it's not specific to that row having two buttons instead of one.

## Measure 2 deviation: stacked PH subsidy enrollments

`sql/m2_returns.sql` (which feeds both the `returns-to-homelessness` KPI tile and the full dashboard's Measure 2 table) deviates from the HUD programming specs by explicit choice: if a client has a still-open PH enrollment that began within 14 days of a qualifying exit (their successful placement), no later PH entry counts as a return to homelessness, however far outside the normal 14-day window it starts. HUD's spec has no provision for a client remaining in that same placement under a second, stacked PH subsidy program (multiple funding sources covering one household's housing) — taken literally, it misreads that second enrollment as a new homelessness episode. Surfaced and confirmed live via `hmisguru/westchester-dac`'s own `wcspm.yml` (that repo's commit history has the full investigation): PersonalID 13523 moved into an open-ended PH placement the day before their qualifying shelter exit and started a second, distinct PH enrollment over a year later — correctly not counted as a return. Regenerate this file (and the other 8) with `scripts/extract_sql.py` whenever `wcspm.yml`'s Measure 2 logic changes; the deviation lives in the dashboard source, not here.

## Zero-length (same-day entry/exit) enrollments

Three fixes to `sql/m1_length_of_time.sql`, `sql/m2_returns.sql`, and `sql/m3_sheltered.sql`, all sourced from `hmisguru/westchester-dac`'s `wcspm.yml` and re-extracted here — see that repo's commit history for the full investigation and live BigQuery confirmation of each:

- **Metric 3.2** (`m3_sheltered.sql`): its `ee_based` active-client test now also requires `ExitDate > EntryDate`, so a same-day ES-EE/TH/SH enrollment (zero documented nights) no longer counts as "active" — it was previously satisfying the period-overlap test despite representing zero nights, which violated the widget's own "Active Clients - Method 5: 1+ Nights Active" methodology.
- **Measure 1** (`m1_length_of_time.sql`): `nbn_earliest` now derives from `nbn_nights` directly instead of re-deriving its own entry/exit bounds, fixing a one-day inconsistency between the two (pure consistency cleanup — same-day enrollments already contributed zero nights to this measure either way).
- **Measure 2** (`m2_returns.sql`): a zero-length candidate enrollment no longer counts as a return to homelessness, **except in Street Outreach** (SO isn't residential — a client can legitimately be contacted as street homeless on a single day, while a same-day ES/TH/SH/PH enrollment is presumed to be a data-entry artifact rather than a genuine re-entry). Also fixed a self-match bug where the very enrollment that produced a client's qualifying "exited to PH" row could, when zero-length, match as its own return — `bucketed` now carries `EnrollmentID` so `matches` can exclude it from matching itself.

## Scheduling

Monthly on the first Wednesday (13:17 UTC), plus on push to `main` and manual dispatch. Cron ORs day-of-month with day-of-week, so the schedule fires every Wednesday (`17 13 * * 3`) and a `schedule-gate` job skips `build`/`deploy` unless the UTC date is the 1st-7th; pushes and manual runs always build. No daily cron — these KPIs only ever change when a new HMIS CSV export lands, which a monthly rebuild already keeps pace with. GitHub disables scheduled workflows in public repos after 60 days of no repo activity; the `keepalive` job re-enables the workflow via the API on each scheduled run to reset that clock.
