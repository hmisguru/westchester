# westchester

Public repo: embeddable HUD System Performance Measure KPIs for the Westchester County CoC (NY-604), built with Observable Framework (`src/`, config in `observablehq.config.js`) and deployed to GitHub Pages (https://hmisguru.github.io/westchester/) by `.github/workflows/deploy.yml`. Companion to the private `hmisguru/westchester-dac` repo (DAC `wcspm.yml` dashboard), which is where the data and query logic come from. There is no project-funding-filter concept here (see "No funding filter" below).

**This repo is public.** Never commit credentials, row-level data, internal service IDs/URLs, or anything from `hmisguru/westchester-dac`'s CLAUDE.md beyond what's needed here. Only CoC-wide aggregates are published. No small-count suppression is applied, per explicit choice: every KPI is a system-wide total or rate.

## Data flow

- `sql/*.sql` are **generated copies** of every `type: table` widget in `wcspm.yml` (System Performance Dashboard, `main` branch of `hmisguru/westchester-dac`) — 9 total, Measures 1, 2, 3.2, 4, 5.1, 5.2, 7a.1, 7b.1, 7b.2 — rendered with no Project filter and with `{{ filters.report_start }}` turned into the BigQuery parameter `@report_start`. Regenerate with `scripts/extract_sql.py <path to wcspm.yml>` whenever the dashboard's measure logic changes; never hand-edit, or the published numbers will drift from the dashboard. 5 of the 9 feed the public KPI tiles (below); all 9 feed the full dashboard page (`/spm/`, see "Full System Performance Dashboard" below). `sql/street_outreach_active.sql` is the one exception in this directory — hand-written, not generated, since it has no `wcspm.yml` widget to copy from; see "People in Street Outreach, Emergency Shelter, or Transitional Housing (non-HUD metric)" below.
- `src/data/spm.json.py` is the KPI-tile data loader, reading from BigQuery project `bruin-508014` (`wchmiscsv`/`clienttrack`-equivalent datasets live there). It reads `MAX(ExportEndDate)` from `wchmiscsv.Export`, reports the most recent **complete** federal fiscal year ending on or before it (FY = Oct 1 – Sep 30), and compares against the prior FY. Measures 1 and 2 are single-period queries, so they run once per FY; 3.2, 5.1, 7a.1 and 7b.1 already return Current/Previous FY columns. It picks one row per measure by exact label and `sys.exit`s if a label is missing, so a changed dashboard query fails the build instead of publishing nulls. (`pick()` previously took a `default` fallback, added for Measure 7a.1's universe row when Westchester had zero Street Outreach projects; removed along with the `street-outreach-exits` tile itself -- see "Street Outreach" below.)
- `src/data/spm-dashboard.json.py` is a second, separate loader for the full dashboard page (`/spm/`) — same fiscal-year logic as `spm.json.py` (duplicated rather than shared, since the two loaders return differently-shaped documents: a handful of picked KPI values vs. every row of all 9 widgets), but runs all 9 widgets in full and keeps every result row, with each widget's own `columns` config (label, number format) copied from `wcspm.yml` so the page renders identically to the dashboard. No `pick()`/`sys.exit` validation here — an empty or reshaped result just renders as an empty table (`spm-dashboard.js`'s `empty()`), matching how DAC itself handles it.
- KPI ids are hardcoded in both the KPI loader (`"id"` fields) and `observablehq.config.js` (`kpiIds`, used for the `/embed/<id>` dynamic paths). Keep the two lists in sync.
- Auth: Application Default Credentials. In CI, the `GCP_SERVICE_ACCOUNT_JSON` repository secret is written to a temp file and pointed to by `GOOGLE_APPLICATION_CREDENTIALS`. This repo's service account needs read-only access to `wcdashboard`/`wchmiscsv` on project `bruin-508014`, scoped to this GCP project alone.

## No funding filter

There is no funded-project-scope split here, per explicit user choice when this repo was commissioned. `hmisguru/westchester-dac`'s `wchmiscsv` has no `Funder` table at all, so there's no equivalent concept to filter by. Every KPI, and `wcspm.yml`'s own Measure 4 (Income Growth) that this repo doesn't surface, is scoped to all TH/SH/PH (or ES/SH/TH, per measure) projects CoC-wide. `kpi.js` has no `scopeData`/`toggle`/funded-scope machinery at all here — there is nothing to toggle.

## Street Outreach

At this repo's creation, the Westchester CoC had zero active Street Outreach (ProjectType 4) projects, confirmed directly against `wchmiscsv.Project`. Per explicit user choice at the time, the `street-outreach-exits` and `exits-to-permanent-housing` tiles were kept unchanged rather than relabeled or dropped, even though `street-outreach-exits` necessarily read 0 for both fiscal years (a correct zero-universe result, not an error) and `exits-to-permanent-housing`'s entire contribution came from 7b.1 (ES/SH/TH/RRH/other PH exits) alone. `sql/m7_exits_to_ph.sql` still unions the 7a.1 `classified` CTE with 7b.1's, so the file needs no special-casing.

As of 2026-10-01, `wchmiscsv` has 17 Street Outreach projects (confirmed live, after a `wchmiscsv` data refresh) — the zero-project state above no longer held by that point, and both tiles reported real, nonzero figures for a while.

**The standalone `street-outreach-exits` tile (HUD Measure 7a.1) was removed entirely, per explicit request** (not relabeled, not zeroed out -- dropped from the KPI grid). `src/data/spm.json.py`: the `"street-outreach-exits"` KPI dict is gone from `build_kpis()`'s `kpis` list, the now-unused `m7a_universe` pick and its `"m7a1"` loader job are both removed, and `pick()` lost its `default` parameter entirely (nothing calls it with one any more -- see the Data flow bullet above). `observablehq.config.js`'s `kpiIds` list dropped `"street-outreach-exits"` too, which also removes its `/embed/street-outreach-exits` page from the build (no further cleanup needed there, since embed pages are generated purely off that array). `exits-to-permanent-housing` is untouched: it's a separate KPI with its own id, and `sql/m7_exits_to_ph.sql` is self-contained (it carries its own copy of Measure 7a.1's CTEs through to `classified`, not a reference to the now-removed `m7a1_street_outreach.sql` loader job), so removing the standalone 7a.1 tile has no effect on it. `sql/m7a1_street_outreach.sql` itself is kept on disk, unused by the loader, as `scripts/extract_sql.py`'s own generator input for `m7_exits_to_ph.sql` -- the same convention already established for `sql/m7b1_placement.sql` above.

## People in Street Outreach, Emergency Shelter, or Transitional Housing (non-HUD metric)

`people-in-street-outreach` is a 7th KPI tile, invented on explicit request rather than drawn from `wcspm.yml` -- **HUD's real SPM spec has no "Measure 3.3"**; Measure 3 only defines 3.1 (PIT counts, not generated from HMIS) and 3.2 (Unduplicated Sheltered Persons). Per explicit choice, this tile drops HUD numbering entirely rather than implying an official measure that doesn't exist. **Originally scoped to Street Outreach alone ("People in Street Outreach"); widened on explicit request to also cover Emergency Shelter and Transitional Housing**, same KPI id and tile position, just a broader universe -- see the bullet below for the scope change itself.

- `kpi.js`'s tile eyebrow normally renders `HUD ${kpi.measure}`; this is the one tile where the KPI object sets `eyebrow` directly (`"Local Measure 3.3"`, per explicit choice -- reads consistently alongside the numbered HUD tiles while still flagging it's not one of them; briefly labeled "Dashboard metric" before that) instead of `measure`, which `renderKpi()` now prefers when present (`kpi.eyebrow ?? \`HUD ${kpi.measure}\``) -- every other tile is unaffected, since none of them set `eyebrow`.
- Not on the `/spm/` full dashboard page -- that page is explicitly a 1:1 rendering of `wcspm.yml`'s own 9 widgets (`spm-dashboard.json.py`'s `WIDGETS` list, "same widget order" per its own docstring), and this metric has no `wcspm.yml` widget to mirror. KPI tiles only.
- `sql/street_outreach_active.sql` is hand-written (see its own header comment) rather than generated by `scripts/extract_sql.py`, since there's no source widget to extract from. It still takes the same `@report_start` BigQuery parameter as every other query (passed via `spm.json.py`'s `run_measure()`, same as the rest), just doesn't reference the unused `@all_projects`/`@project_ids` parameters that `run_measure()` always supplies -- confirmed live that BigQuery accepts declared-but-unreferenced named parameters without error.
- **Scope: `ProjectType IN (0, 1, 2, 4)`, CoC-participating projects, per explicit request to widen from Street Outreach alone.** In this CoC's own `Project.csv`, ProjectType 0 and 1 are both Emergency Shelter (Entry/Exit and Night-by-Night tracking, respectively), 2 is Transitional Housing, and 4 is Street Outreach -- confirmed against live data, not the usual HUD ProjectType numbering convention for ES/TH. `EnrollmentCoC = 'NY-604'` OR null is still included (same convention as the rest of this file's queries; confirmed live that including null-CoC rows adds 34 people to the FY2026 figure who have no `NY-604`-coded enrollment row at all among their qualifying enrollments).
- **Universe, modeled on Metric 3.2's comparison layout, split by project type per explicit follow-up request**: `es_th_active` (ProjectType 0, 1, 2) applies Metric 3.2's own zero-length-enrollment exclusion (`ExitDate > EntryDate`, same test as `sql/m3_sheltered.sql`'s `ee_based` CTE), while `so_active` (ProjectType 4) keeps the original no-exclusion test, since Street Outreach isn't residential and a client can legitimately be contacted as street homeless on a single day with no multi-day enrollment span to speak of (the same reasoning already applied to Measure 2's return-to-homelessness matching, `sql/m2_returns.sql`'s `has_duration` flag). The two CTEs are combined with `UNION DISTINCT` before the final unduplicated count, so a person active in both groups still counts once. **This replaced an earlier version that applied the no-exclusion test uniformly across all 4 project types** (documented in this file's own prior revision) -- that version is no longer current. Confirmed live (`report_start = 2025-10-01`): **3,961 current FY (FY2026) vs. 4,354 previous FY (FY2025)** -- down from 4,030/4,439 under the no-split version (69 and 85 people respectively had only same-day ES/TH enrollments), and up from the original Street-Outreach-only figures of 336 current FY / 486 previous FY.
- `better: None` (neutral gray arrow, no Improved/Worsened label): neither direction is inherently better, since fewer people found could mean less homelessness or just less outreach/shelter contact.
- **No "people" unit label after the tile's number, per explicit request** — this tile previously set `"unit": "people"` like most other count-based KPIs here, which `kpi.js`'s `formatValue()` renders as a `.wkpi-unit` span right after the figure (e.g. "4,030 people"). Dropped the `unit` key entirely so `formatValue()`'s `number` case falls back to its own default (`kpi.unit ?? ""`, i.e. no suffix) -- the tile now shows the bare number. Scoped to this one tile only; every other KPI here that sets `"unit": "people"` (e.g. `returns-to-homelessness`) is unaffected.
- Considered and rejected as the universe definition: a `CurrentLivingSituation = 116` ("place not meant for habitation") contact-based count, mirroring a stricter "currently unsheltered" convention more closely (confirmed live under the original Street-Outreach-only scope: 149 current FY vs. 243 previous FY under that definition). Not used, per explicit choice for the simpler enrollment-overlap definition instead, matching Measure 3.2's own approach more directly.
- **The plain HUD Measure 3.2 tile (`people-sheltered`, "People in shelter or transitional housing") was removed from the KPI grid entirely, per explicit request** -- this tile's own universe (ES/SH/TH, no Street Outreach) sits conceptually inside this one's wider ES/SH/TH/Street-Outreach universe, so it was judged redundant once Local 3.3 existed. `src/data/spm.json.py`: dropped the `"people-sheltered"` KPI dict and its `m3` pick and `"m3"` loader job (`sql/m3_sheltered.sql` itself stays on disk -- `spm-dashboard.json.py`'s separate loader still needs it for the real Measure 3.2 widget on `/spm/`, and this section's own design-rationale citations of "Metric 3.2's" SQL patterns above still refer to that same file). `observablehq.config.js`'s `kpiIds` dropped `"people-sheltered"` too, removing its `/embed/people-sheltered` page. Unlike the Measure 5.1/Local 5.3 pair, Local 3.3 was NOT relabeled to take over Measure 3.2's plain title -- it keeps its own "Local Measure 3.3" eyebrow and full title, since its scope is visibly broader (ES/SH/TH/Street Outreach, not just ES/SH/TH) rather than a like-for-like replacement.

## First-time homelessness including Street Outreach (Local Measure 5.3, non-HUD metric)

`first-time-homeless-with-outreach` is a KPI tile, invented on explicit request as an enhanced version of HUD Measure 5.1 ("People experiencing homelessness for the first time") that also counts Street Outreach contact. **Named "Local Measure 5.3" only after confirming `wcspm.yml` has no real HUD Measure 5.3 to collide with** -- unlike the number 5.2, which *is* taken (a real HUD widget, "Measure 5.2 — First-Time Homeless (ES, SH, TH, PH)", `sql/m5_2_first_time_ph.sql`, shown on `/spm/`; that one adds Permanent Housing, not Street Outreach, and is a completely different definition from this tile).

- `sql/m5_3_first_time_so.sql` is hand-written (see its own header comment) rather than generated by `scripts/extract_sql.py`, since there's no source widget to extract from -- a near-verbatim copy of `sql/m5_first_time.sql`'s own Measure 5.1 logic (same `entries`/`client_start`/`prior_history` CTE structure, same 7-year/730-day lookback rule, same `EnrollmentCoC = 'NY-604'` OR null convention), with Street Outreach (ProjectType 4) added to both project-type lists.
- **Scope: Street Outreach added to both `entry_projects` and `scan_projects`, per explicit request** -- `entry_projects` (the population being checked) becomes `ProjectType IN (0, 1, 2, 4, 8)`, and `scan_projects` (what counts as "prior activity" when deciding if someone is first-time) becomes `ProjectType IN (0, 1, 2, 3, 4, 8, 9, 10, 13)`. Symmetric by design: a person entering via Street Outreach counts toward the population, and prior Street Outreach contact disqualifies someone else as "first time" the same way prior ES/TH/SH/PH contact already does. (HUD's own Measure 5.1 keeps Street Outreach out of both lists entirely; `scan_projects` already included PSH (ProjectType 3), PH-Housing Only (9), PH-Housing with Services (10), and RRH (13) before this change -- see `sql/m5_first_time.sql` for the unmodified baseline. Note ProjectType 10 is a non-RRH PH subtype in this dataset, not RRH itself -- RRH is 13; see the Measure 7b.2 section below for where this distinction matters.)
- `better: "lower"`, same direction as Measure 5.1 itself: fewer newly-homeless people is the improvement.
- Not on the `/spm/` full dashboard page, same reasoning as `people-in-street-outreach` above -- that page is explicitly a 1:1 rendering of `wcspm.yml`'s own 9 widgets, and this metric has no `wcspm.yml` widget to mirror.
- **The plain HUD Measure 5.1 tile (`first-time-homeless`) was removed from the KPI grid entirely, per explicit follow-up request, and this tile relabeled to take over its plain title ("People experiencing homelessness for the first time") and tile position** -- so there's now one first-time-homelessness tile on the grid, not two, with Local Measure 5.3's wider (ES/SH/TH/Street Outreach) definition standing in for HUD's narrower one. `src/data/spm.json.py`: the `"first-time-homeless"` KPI dict, its `m5` pick, and the `"m5"` loader job are all gone (`sql/m5_first_time.sql` itself stays on disk -- `spm-dashboard.json.py`'s separate loader still needs it for the real Measure 5.1 widget on `/spm/`). `observablehq.config.js`'s `kpiIds` dropped `"first-time-homeless"` too, removing its `/embed/first-time-homeless` page. `eyebrow` ("Local Measure 5.3") is unchanged -- only `title` changed, so the tile still visibly flags that it isn't a plain numbered HUD measure even while reading as the dashboard's de facto "first-time homelessness" tile. The home page's "About this data" note (`src/index.md`) was rewritten to describe both non-HUD tiles (3.3 and 5.3) and their reasoning, not just 3.3.
- **Verification: confirmed to run without error against live BigQuery data** -- PR #41's merge build (deploy run #53, the first real execution of `m5_3_first_time_so.sql` in CI) completed successfully. This session's own `Google_Cloud_BigQuery` MCP connection needed re-authentication throughout this measure's build and still hadn't been restored by the time Measure 5.1 was removed, so the actual current/previous FY figures haven't been independently pulled and sanity-checked by this session -- only that the query executes cleanly in production. Confirm the real numbers live and update this note once BigQuery access is restored.

## Permanent Housing Retention (Measure 7b.2)

`permanent-housing-retention` is a KPI tile for the real HUD widget "Measure 7b.2 — Successful Placement/Retention in Permanent Housing," per explicit request. Unlike Local Measures 3.3 and 5.3, this one is a genuine numbered HUD measure, so its `eyebrow` isn't set -- `kpi.js`'s default `HUD ${kpi.measure}` rendering (`"measure": "Measure 7b.2"`) applies, same as every other plain HUD tile.

- `sql/m7b2_retention.sql` already existed (generated from `wcspm.yml`, used by `spm-dashboard.json.py`'s loader for the `/spm/` full dashboard page) before this tile was added -- no new SQL was written. Its own `'% Successful exits/retention'` row (`ROUND(SAFE_DIVIDE(stayer_cnt + leaver_permanent_cnt, stayer_cnt + leaver_cnt) * 100, 2)`) is pulled directly for this tile's `value`/`previous`, and its `'Universe: PH-PSH/HO/HS stayers and leavers with move-in'` row for `universe`.
- **Universe: people in PSH, PH-Housing Only, or PH-Housing with Services (`ProjectType IN (3, 9, 10)`) who either stayed housed through the report period (with a confirmed move-in) or exited during it (with a confirmed move-in)** -- the same `own_movein`/`hoh_movein`/`effective_movein` Head-of-Household-inherited move-in logic `sql/m7b2_retention.sql`'s sibling files already use elsewhere in this repo. **RRH (ProjectType 13) is deliberately excluded**, confirmed correct against HUD's own System Performance Measures HMIS Programming Specifications (p.44): Metric 7b.2's universe is explicitly "all PH projects except PH-RRH." `sql/m7b2_retention.sql`'s own `wcspm.yml` source widget description already states this intent plainly ("types 3, 9, 10 -- excludes PH-RRH") -- this was double-checked against the actual HUD spec PDF after an initial, incorrect assumption in this session that ProjectType 10 meant RRH (it doesn't; RRH is 13). A person "succeeds" if they're still housed as of `report_end`, or if they exited to a destination coded 400-499 (another permanent destination); the same 4-code exclude list as `sql/m7b1_placement.sql` (`206, 215, 225, 24`) drops non-informative exits from the universe entirely rather than counting them as failures.
- `format: "percent"`, `better: "higher"` -- the first percent-formatted tile in this loader. `kpi.js`'s `formatValue()`/`describeChange()`/`statusOf()` already handle `"percent"` generically (one-decimal display, "N.N pts higher/lower than FY20XX" wording, a tighter 0.05 "unchanged" epsilon than the 0.5 used for raw counts) -- confirmed by reading that code, not guessed; no renderer changes were needed to add this tile. The SQL's own `ROUND(..., 2)` output is already on a 0-100 scale, matching what `formatValue()` expects (it appends a bare `%` suffix, not a `style: "percent"` formatter that would also need a 0-1 fraction).
- **Does this measure's universe double-count with `exits-to-permanent-housing` (Measures 7a.1 + 7b.1)?** No -- that tile's universe is Street Outreach/ES/SH/TH/RRH participants *not yet in permanent housing* exiting to it for the first time (7b.1's own widget name spells out "ES, SH, TH, PH-RRH, PH exits without move-in"); this tile's universe is PSH/PH-Housing-Only/PH-Housing-with-Services participants *already moved into* permanent housing, excluding RRH entirely, tracking whether they stay housed or move on to another permanent destination. Different populations (RRH shows up in 7a.1+7b.1's universe, never in 7b.2's), no overlap.
- **Verification note: not yet confirmed live against BigQuery** -- same `Google_Cloud_BigQuery` MCP re-authentication gap documented above for Local Measure 5.3 is still open as of this tile's addition. Unlike that measure, `sql/m7b2_retention.sql` is not new code (it's the same file `/spm/` has used successfully in production for a while), so the risk of a build-breaking query error is low -- but the actual current/previous FY percentage hasn't been independently pulled and sanity-checked by this session. Confirm the real numbers live and update this note once BigQuery access is restored.

## Full System Performance Dashboard (`/spm/`)

A static Observable rendering of every measure widget in `wcspm.yml`, not just the 5 summarized as KPI tiles, built on explicit request. Per explicit instruction, it's modeled on a fuller dashboard-notes template rather than `wcspm.yml` alone, since the two had drifted: `wcspm.yml` (`hmisguru/westchester-dac`, `main`) is missing that template's "Dashboard Notes" intro widget entirely, and lists its 9 measure widgets in a different row order (Measure 3.2 first, rather than Measures 1a/1b first). `src/spm/index.md` follows that template's order and includes an adapted version of its notes text (`renderNotes()` in `spm-dashboard.js`) — `wcspm.yml` itself was NOT changed to match; that's a separate, not-yet-requested fix in the `hmisguru/westchester-dac` repo.

- **CoC-wide only, no interactive filters** — per explicit choice, this page shows only CoC-wide figures for the current vs. previous fiscal year, refreshed only when the site rebuilds. There is no Fiscal Year Start Date control (same reasoning the public KPI tiles already use in `spm.json.py`'s `run_measure()`: `report_start` is a continuous date, so there's no finite set of values to precompute) and no Project filter.
- **A per-project single-select dropdown existed briefly and was archived, not deleted** — per explicit request. It ran every one of the 9 widgets once CoC-wide and once per "active SPM project" (open, HUD-SPM-covered project type; 121 of 179 `ContinuumProject = 1` projects as of 2026-10-01) — 9 × 122 = 1,098 BigQuery queries per build, confirmed to complete in under 2 minutes in CI. The full working loader (`spm-dashboard.json.py`), renderer (`spm-dashboard.js`), and the CSS it needs (`spm-dashboard.css`) are preserved at `archive/`, with a README there on how to reactivate it. A multi-select was never built: several widgets' per-person dedup logic (returns, first-time, retention) spans the whole selected universe at once, so summing two projects' independently-precomputed rows would double-count clients active in both — each dropdown option had to be its own full, independently-correct query, not a combination of smaller pieces.
- Widget order and titles match `wcspm.yml` exactly (which already differs from that template in two places by explicit design, not drift: Measure 4's title and its broader TH/SH/PH-not-CoC-funded-only scope, documented under "No funding filter" above).
- `src/components/spm-dashboard.js`/`.css` render it: `renderNotes()` for the intro box, `renderDashboard()` for the 9 measure tables (plain HTML tables via each widget's own `columns` config — no conditional-format pills, since none of `wcspm.yml`'s table columns use them). Class prefix `spmd-`, distinct from `kpi.js`'s `wkpi-` and the rest of the site, since this isn't an embeddable module.
- **`renderNotes()`'s box renders below the 9 tables, not above them, collapsed behind a native `<details>/<summary>`** ("About this data", per explicit request) — the tables are the first thing in view rather than being pushed down by that long paragraph. `spm/index.md`'s own script cell wraps the `<div class="spmd-notes">` `renderNotes()` returns in a `<details class="spmd-notes-details">`; `.spmd-notes` itself (the box background/border/padding) is untouched, only its position and this wrapper changed. `.spmd-notes-details`'s summary styling lives in `spm-dashboard.css`, lightweight to match `index.md`'s own `.note-details` convention.
- Linked from the KPI homepage (`src/index.md`) and links back to it; not added to `dynamicPaths` (no embed/iframe variant requested for this page, unlike the KPI tiles).
- **Light/dark toggle, default light** — `renderThemeToggle()` in `spm-dashboard.js` sets `document.documentElement.dataset.theme`, persisted in `localStorage` (`spmd-theme`) so a return visit keeps the visitor's last choice, but every first-ever visit starts light regardless. Unlike `kpi.js`'s `data-theme` option (a prop the embedding page sets once, no UI), this is a visible button the visitor clicks, since `/spm/` is a standalone page rather than an embedded tile. The dark palette reuses `kpi.js`'s own `data-theme="dark"` colors (`#02372d` surface, `#3dc372` accent, white text) for consistency with the KPI tiles elsewhere on this site. Implementation note: rather than switching Framework's own `theme:` config (which only supports OS-preference-driven `prefers-color-scheme` dual themes, not a manual toggle), `spm-dashboard.css` overrides Framework's `--theme-foreground`/`--theme-background-*` custom properties under `html[data-theme="dark"]` — higher specificity than Framework's own `:root` declarations, same element — which flips the page background/text/link color for free via `global.css`'s existing `var()` consumption; only `.spmd-*`'s own hardcoded-hex colors need explicit dark overrides.
- **The KPI home page (`src/index.md`) reuses this same toggle**, importing `renderThemeToggle()` directly from `spm-dashboard.js` and linking `spm-dashboard.css`, rather than building a near-duplicate — a deliberate choice to share the `spmd-theme` localStorage key across both pages, since they're tightly coupled views of the same KPI dataset and already cross-link to each other in-page. `renderKpiGrid()`'s own theme is a prop set once at render time, not a `[data-theme]` cascade, so `index.md`'s script cell also pushes the toggle's current state onto the grid wrapper and each `.wkpi` tile by hand (on load and again on every toggle click) to keep the tiles in sync; `kpi.js` itself is untouched, since it's published externally via `dynamicPaths`. The home page's "About this data" note is also collapsed behind a native `<details>/<summary>` (`.note-details` in `index.md`'s own `<style>` block), lightweight by design since the note had no CSS before that either.
- **Share controls (copy link, email) — built, currently unused, per explicit request.** `src/components/share.js`/`.css` hold a working, page-agnostic `renderShareControls()` (a "Copy link" button via the Clipboard API with a graceful text-only fallback if it's unavailable, plus an "Email" `mailto:` link prefilled with a subject/body each page would pass in and the current page URL), styled to match `.spmd-theme-toggle`'s pill shape/palette. Neither `index.md` nor `spm/index.md` imports or links it right now — shipped once, then explicitly hidden shortly after without being deleted, so it's a quick re-add (import + link tag + appending its result into `.page-controls` alongside the toggle, same as before) rather than a rebuild if it's wanted again later. `.page-controls`'s own `margin-top: 8px` (see the toggle bullet above) stays regardless of whether share controls are present — it's not specific to that row having two buttons instead of one.

## Measure 2 deviation: stacked PH subsidy enrollments

`sql/m2_returns.sql` (which feeds both the `returns-to-homelessness` KPI tile and the full dashboard's Measure 2 table) deviates from the HUD programming specs by explicit choice: if a client has a still-open PH enrollment that began within 14 days of a qualifying exit (their successful placement), no later PH entry counts as a return to homelessness, however far outside the normal 14-day window it starts. HUD's spec has no provision for a client remaining in that same placement under a second, stacked PH subsidy program (multiple funding sources covering one household's housing) — taken literally, it misreads that second enrollment as a new homelessness episode. Surfaced and confirmed live via `hmisguru/westchester-dac`'s own `wcspm.yml` (that repo's commit history has the full investigation): PersonalID 13523 moved into an open-ended PH placement the day before their qualifying shelter exit and started a second, distinct PH enrollment over a year later — correctly not counted as a return. Regenerate this file (and the other 8) with `scripts/extract_sql.py` whenever `wcspm.yml`'s Measure 2 logic changes; the deviation lives in the dashboard source, not here.

## Zero-length (same-day entry/exit) enrollments

Three fixes to `sql/m1_length_of_time.sql`, `sql/m2_returns.sql`, and `sql/m3_sheltered.sql`, all sourced from `hmisguru/westchester-dac`'s `wcspm.yml` and re-extracted here — see that repo's commit history for the full investigation and live BigQuery confirmation of each:

- **Metric 3.2** (`m3_sheltered.sql`): its `ee_based` active-client test now also requires `ExitDate > EntryDate`, so a same-day ES-EE/TH/SH enrollment (zero documented nights) no longer counts as "active" — it was previously satisfying the period-overlap test despite representing zero nights, which violated the widget's own "Active Clients - Method 5: 1+ Nights Active" methodology.
- **Measure 1** (`m1_length_of_time.sql`): `nbn_earliest` now derives from `nbn_nights` directly instead of re-deriving its own entry/exit bounds, fixing a one-day inconsistency between the two (pure consistency cleanup — same-day enrollments already contributed zero nights to this measure either way).
- **Measure 2** (`m2_returns.sql`): a zero-length candidate enrollment no longer counts as a return to homelessness, **except in Street Outreach** (SO isn't residential — a client can legitimately be contacted as street homeless on a single day, while a same-day ES/TH/SH/PH enrollment is presumed to be a data-entry artifact rather than a genuine re-entry). Also fixed a self-match bug where the very enrollment that produced a client's qualifying "exited to PH" row could, when zero-length, match as its own return — `bucketed` now carries `EnrollmentID` so `matches` can exclude it from matching itself.

## Coordinated Entry prototype (`/coordinated-entry/`)

- A dashboard built directly against `wchmiscsv`'s own HUD Coordinated Entry (CE) data elements -- `CEParticipation` (2.09), `Assessment` (4.19), `Event` (4.20) -- rather than from a DAC YAML like every other dashboard above. - **Report universe: `Project.ProjectType = 14`, per explicit request** -- every `sql/ce_*.sql` file's `ce_projects` CTE now reads `WHERE p.ContinuumProject = 1 AND p.ProjectType = 14` (the same `ContinuumProject`-plus-`ProjectType` pattern `sql/m3_sheltered.sql`/`sql/m5_first_time.sql` already use elsewhere in this repo). **This deliberately departs from the CE APR spec's own universe definition**, which this dashboard used from its first build through PR #49: the spec counts a project as Coordinated Entry if it has a `CEParticipation` record with `AccessPoint = 1` overlapping the period, regardless of HMIS `ProjectType` -- broader than `ProjectType = 14` alone, since a CE access point in this dataset can be typed as something else entirely (e.g. an Emergency Shelter that also screens walk-ins). Rescoping to `ProjectType = 14` only will silently exclude those projects' CE activity; that's the explicit, intended effect of this change, not an oversight. `CEParticipation` is no longer referenced anywhere in `sql/ce_*.sql`.
- **Monthly granularity over the federal fiscal year, per explicit request** -- every other dashboard/KPI on this site compares fiscal-year-over-fiscal-year or quarter-over-quarter; this one trends all 12 calendar months of the current FY and highlights month-over-month change instead, for more granular detail on a system that moves client-by-client rather than in big year-over-year swings. `src/data/coordinated-entry.json.py` runs each `sql/ce_*.sql` query once per month (12 BigQuery jobs per file, not 1-2 like the FY-comparison loaders), taking `@period_start`/`@period_end` directly rather than the `sql/m*.sql` files' implicit "+1 year" window.
- **No prioritization slice, per explicit instruction** -- this CoC's CE process currently prioritizes everyone with an assessment by default (a placeholder policy), not a real differentiated prioritization score; a tile breaking out "prioritized vs. not" would just show 100%/0% and mean nothing. Revisit once prioritization scores are available via API (the CE APR's own Q9b: Prioritization Status) -- don't build this tile on today's data even though `Assessment.PrioritizationStatus` exists in the schema.
- **Slice 1: Reach (`sql/ce_reach.sql`)** -- Persons/Households with a CE Assessment each month, broken out by household type (Without Children / With Children and Adults / With Only Children / Unknown Household Type), modeled on the CE APR's own Q7a/Q8a/Q9a table shape. For a household assessed more than once in a month, uses its latest assessment date in that month (the spec's own "latest assessment" rule, applied per-month instead of per-report-year). Household type is computed from age at that assessment date (adult >= 18, same age-math pattern as `sql/m*.sql` files elsewhere use for this), over every household member active (the repo's own "Active Clients" convention) as of that date -- not the assessment's own `RelationshipToHoH`-based household composition the literal spec describes, a deliberate simplification for a monthly trend view.

Counts households, not persons, matching the spec's own Q9a shape -- unlike Reach, which reports both.

Kept here for history -- the shortened-label and "Other"-folding techniques this slice introduced are still used/referenced elsewhere in this file.

All three rate/breakdown tiles have since been removed, each per its own explicit request, leaving only the `event_outcomes` CTE (the combined-chart cross-tab below). ## Scheduling

Monthly on the first Wednesday (13:17 UTC), plus on push to `main` and manual dispatch. Cron ORs day-of-month with day-of-week, so the schedule fires every Wednesday (`17 13 * * 3`) and a `schedule-gate` job skips `build`/`deploy` unless the UTC date is the 1st-7th; pushes and manual runs always build. No daily cron — these KPIs only ever change when a new HMIS CSV export lands, which a monthly rebuild already keeps pace with. GitHub disables scheduled workflows in public repos after 60 days of no repo activity; the `keepalive` job re-enables the workflow via the API on each scheduled run to reset that clock.
